RentPro API Response Guide

One response format for every endpoint in RentPro (ASP.NET Core Web API). Pick the section for your HTTP method, then return the matching status code and body.

1. The response envelope

Every response, success or failure, uses this shape.

{
  "success": true,
  "data": null,
  "message": null,
  "errors": null
}
FieldTypeMeaning
successbooltrue for 2xx, false for everything else
dataobject / array / nullThe DTO on success. Always null on failure
messagestring / nullShort text for the user
errorsobject / nullField errors, filled only for validation (400). Otherwise null

Rules for every endpoint

  1. Status code and success always agree. Never return 200 with "success": false.
  2. data is null whenever success is false.
  3. errors is only for validation (400). Every other failure explains itself in message.
  4. A 500 never shows the real exception text. Return a generic message and log the real error.
  5. Never return secrets. No PasswordHash, no other user's tokens, in any response.

CodeWhen to use it

Security rules

Login

Same message for an unknown email and a wrong password, so nobody can test which emails are registered.

Forgot password

Always 200 with the same message, whether or not the email exists.

Change password

No UserId in the request. The user comes from the token.

Inactive / banned users

Refuse login with 403. Never issue a token with a warning.

12. C# classes

ApiResponse<T>

Suggested location: Rent.API/Common/ApiResponse.cs. It's an HTTP concern; the Application layer keeps returning plain DTOs.

C#
public class ApiResponse<T>
{
    public bool Success { get; set; }
    public T? Data { get; set; }
    public string? Message { get; set; }
    public Dictionary<string, string[]>? Errors { get; set; }
}

PaginationQuery

Base class for list requests. Endpoint-specific queries inherit from it.

C#
using System.ComponentModel.DataAnnotations;

public class PaginationQuery
{
    [Range(1, int.MaxValue, ErrorMessage = "Page must be 1 or greater.")]
    public int Page { get; set; } = 1;

    [Range(1, 100, ErrorMessage = "PageSize must be between 1 and 100.")]
    public int PageSize { get; set; } = 20;

    [MaxLength(100)]
    public string? Search { get; set; }

    public string? SortBy { get; set; }

    [RegularExpression("^(asc|desc)$", ErrorMessage = "SortOrder must be 'asc' or 'desc'.")]
    public string SortOrder { get; set; } = "desc";
}

public class PropertyQuery : PaginationQuery
{
    [MaxLength(100)]
    public string? City { get; set; }
}

PagedResponse<T>

The calculated fields are worked out from the stored ones, so they can never disagree.

C#
public class PagedResponse<T>
{
    public List<T> Items { get; set; } = new();
    public int Page { get; set; }
    public int PageSize { get; set; }
    public int TotalCount { get; set; }

    public int TotalPages => (int)Math.Ceiling(TotalCount / (double)PageSize);
    public bool HasPrevious => Page > 1;
    public bool HasNext => Page < TotalPages;
}

A list endpoint returns ApiResponse<PagedResponse<PropertySummaryResponse>>.
