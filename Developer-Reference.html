API Response Guide

One response format for every endpoint in an ASP.NET Core Web API. Pick the section for your HTTP method, then return the matching status code and body.

1. The response envelope

Every response, success or failure, uses this shape.

{
  "success": true,
  "data": null,
  "message": null,
  "errors": null
}
FieldTypeMeaning
successbooltrue for 2xx, false for everything else
dataobject / array / nullThe DTO on success. Always null on failure
messagestring / nullShort text for the user
errorsobject / nullField errors, filled only for validation (400). Otherwise null

Rules for every endpoint

  1. Status code and success always agree. Never return 200 with "success": false.
  2. data is null whenever success is false.
  3. errors is only for validation (400). Every other failure explains itself in message.
  4. A 500 never shows the real exception text. Return a generic message and log the real error.
  5. Never return secrets. No PasswordHash, no other user's tokens, in any response.

Security rules

Login

Same message for an unknown email and a wrong password, so nobody can test which emails are registered.

Forgot password

Always 200 with the same message, whether or not the email exists.

Change password

No UserId in the request. The user comes from the token.

Inactive / banned users

Refuse login with 403. Never issue a token with a warning.

{

PaginationQuery

Base class for list requests. Endpoint-specific queries inherit from it.

C#
using System.ComponentModel.DataAnnotations;

public class PaginationQuery
{
    [Range(1, int.MaxValue, ErrorMessage = "Page must be 1 or greater.")]
    public int Page { get; set; } = 1;

    [Range(1, 100, ErrorMessage = "PageSize must be between 1 and 100.")]
    public int PageSize { get; set; } = 20;

    [MaxLength(100)]
    public string? Search { get; set; }

    public string? SortBy { get; set; }

    [RegularExpression("^(asc|desc)$", ErrorMessage = "SortOrder must be 'asc' or 'desc'.")]
    public string SortOrder { get; set; } = "desc";
}

public class PropertyQuery : PaginationQuery
{
    [MaxLength(100)]
    public string? City { get; set; }
}

PagedResponse<T>

The calculated fields are worked out from the stored ones, so they can never disagree.

C#
public class PagedResponse<T>
{
    public List<T> Items { get; set; } = new();
    public int Page { get; set; }
    public int PageSize { get; set; }
    public int TotalCount { get; set; }

    public int TotalPages => (int)Math.Ceiling(TotalCount / (double)PageSize);
    public bool HasPrevious => Page > 1;
    public bool HasNext => Page < TotalPages;
}

A list endpoint returns ApiResponse<PagedResponse<PropertySummaryResponse>>.

Relationships with the Fluent API

Every relationship type shown twice: the Data Annotation way and the Fluent API way, using modelBuilder in OnModelCreating. The examples use a small library and school model so each one stands on its own.

1. Why Fluent API

Both styles produce the same database. The difference is where the rules live.

Data AnnotationsFluent API
Where rules liveAttributes on entity classes (Domain)OnModelCreating in the DbContext (Infrastructure)
Domain depends on EF Core?Yes, for [Index], [Precision], [DeleteBehavior], [PrimaryKey]No. Entities are plain C# classes
Covers everything?No. No identity seed, check constraints, default SQL…Yes. Everything annotations can do, and more
PrecedenceFluent API > Data Annotations > Conventions. If both are set, Fluent API wins
[Key], [Required], [MaxLength], [ForeignKey] and [InverseProperty] come from System.ComponentModel.DataAnnotations, not from EF Core. Only the EF-specific attributes listed above add the EF Core package to Domain. Moving everything to Fluent API removes both kinds from your entities.

2. Setup with ModelBuilder

Where the files go

Structure
MyApp.Domain
└── Entities
    ├── Author.cs            ← plain classes, no using Microsoft.EntityFrameworkCore
    └── Book.cs

MyApp.Infrastructure
└── Persistence
    └── AppDbContext.cs      ← all Fluent API rules in OnModelCreating

All rules in OnModelCreating

AppDbContext.cs
using Microsoft.EntityFrameworkCore;

public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    public DbSet<Author> Authors => Set<Author>();
    public DbSet<Book> Books => Set<Book>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Author>(entity =>
        {
            entity.ToTable("Authors");
            entity.HasKey(a => a.Id);
            entity.Property(a => a.Name).IsRequired().HasMaxLength(100);
        });

        modelBuilder.Entity<Book>(entity =>
        {
            entity.ToTable("Books");
            entity.HasKey(b => b.Id);
            entity.Property(b => b.Title).IsRequired().HasMaxLength(200);

            // relationships go here (see the sections below)
        });
    }
}

Two ways to write the same thing

BLOCK STYLE (used in this guide)
C#
modelBuilder.Entity<Book>(entity =>
{
    entity.HasKey(b => b.Id);
    entity.Property(b => b.Title).HasMaxLength(200);
});
ONE STATEMENT PER RULE
C#
modelBuilder.Entity<Book>().HasKey(b => b.Id);
modelBuilder.Entity<Book>().Property(b => b.Title).HasMaxLength(200);

When OnModelCreating gets long: split per entity

Still plain ModelBuilder, just moved into static methods so each entity has its own file.

Persistence/Configurations/BookModel.cs
public static class BookModel
{
    public static void Configure(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Book>(entity =>
        {
            entity.HasKey(b => b.Id);
            entity.Property(b => b.Title).IsRequired().HasMaxLength(200);
        });
    }
}
AppDbContext.cs
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    AuthorModel.Configure(modelBuilder);
    BookModel.Configure(modelBuilder);
}

Rules

  1. One modelBuilder.Entity<T> block per entity. Keep all of that entity's rules together.
  2. Configure each relationship once, usually in the block of the entity that holds the FK (the dependent side). Configuring it from both sides works, but both must agree.
  3. Don't mix styles for the same rule. Pick Fluent API and remove the attribute, or the two can quietly disagree.
  4. Lambdas are compile-checked. b => b.Author breaks the build if you rename the property, unlike strings.

3. Reading a relationship chain

Every relationship is one sentence, read left to right.

C#
modelBuilder.Entity<Book>(entity =>
{
    entity.HasOne(b => b.Author)              // a Book has one Author
          .WithMany(a => a.Books)             // an Author has many Books
          .HasForeignKey(b => b.AuthorId)     // linked by Book.AuthorId
          .IsRequired()                       // every Book must have an Author
          .OnDelete(DeleteBehavior.Restrict); // can't delete an Author who still has Books
});
MethodMeaningAnnotation it replaces
HasOne(x => x.Nav)This entity points to one of the otherSingle navigation property
HasMany(x => x.Navs)This entity has many of the otherCollection property
WithOne(x => x.Nav)The other side points back to one[InverseProperty]
WithMany(x => x.Navs)The other side has many[InverseProperty]
HasForeignKey(x => x.FkId)Which property is the FK[ForeignKey]
IsRequired() / IsRequired(false)FK must / may be nullint vs int?
OnDelete(...)What happens to children when the parent is deleted[DeleteBehavior]
No navigation on the other side? Leave the lambda empty: .WithMany() or .WithOne().

One Author writes many Books. Each Book has exactly one Author.

Domain/Entities
using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;
using Microsoft.EntityFrameworkCore;   // for [DeleteBehavior]

public class Author
{
    [Key]
    public int Id { get; set; }

    [Required, MaxLength(100)]
    public string Name { get; set; } = string.Empty;

    [InverseProperty(nameof(Book.Author))]
    public ICollection<Book> Books { get; set; } = new List<Book>();
}

public class Book
{
    [Key]
    public int Id { get; set; }

    [Required, MaxLength(200)]
    public string Title { get; set; } = string.Empty;

    public int AuthorId { get; set; }

    [ForeignKey(nameof(AuthorId))]
    [InverseProperty(nameof(Author.Books))]
    [DeleteBehavior(DeleteBehavior.Restrict)]
    public Author Author { get; set; } = null!;
}
FLUENT API
Domain/Entities (plain)
public class Author
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public ICollection<Book> Books { get; set; } = new List<Book>();
}

public class Book
{
    public int Id { get; set; }
    public string Title { get; set; } = string.Empty;
    public int AuthorId { get; set; }
    public Author Author { get; set; } = null!;

AppDbContext.OnModelCreating
modelBuilder.Entity<Author>(entity =>
{
    entity.HasKey(a => a.Id);
    entity.Property(a => a.Name).IsRequired().HasMaxLength(100);
});

modelBuilder.Entity<Book>(entity =>
{
    entity.HasKey(b => b.Id);
    entity.Property(b => b.Title).IsRequired().HasMaxLength(200);

    entity.HasOne(b => b.Author)
          .WithMany(a => a.Books)
          .HasForeignKey(b => b.AuthorId)
          .IsRequired()
          .OnDelete(DeleteBehavior.Restrict);
});
The FK goes on the many side (Book). The collection goes on the one side (Author). No unique index on AuthorId.

AppDbContext.OnModelCreating
modelBuilder.Entity<UserProfile>(entity =>
{
    entity.Property(p => p.Bio).HasMaxLength(500);

In one-to-one, EF can't guess which side is the dependent, so HasForeignKey<T> names the entity that holds the FK. EF automatically creates a unique index on UserId; that unique index is what makes it one-to-one in the database.

An Enrollment links a Student and a Course and stores the enrolment date and grade. It's really two one-to-many relationships.

DATA ANNOTATIONS
Domain/Entities
[Index(nameof(StudentId), nameof(CourseId), IsUnique = true)] // EF Core attribute
public class Enrollment
{
    [Key]
    public int Id { get; set; }

    public int StudentId { get; set; }
    [ForeignKey(nameof(StudentId))]
    [InverseProperty(nameof(Student.Enrollments))]

    public Course Course { get; set; } = null!;

FLUENT API
Enrollment.cs (plain)
public class Enrollment
{
    public int Id { get; set; }
    public int StudentId { get; set; }
    public Student Student { get; set; } = null!;
    public int CourseId { get; set; }
    public Course Course { get; set; } = null!;
    public DateOnly EnrolledOn { get; set; }
    public string? Grade { get; set; }

AppDbContext.OnModelCreating
modelBuilder.Entity<Enrollment>(entity =>
{
    entity.HasKey(e => e.Id);

    // a student can't enrol in the same course twice
    entity.HasIndex(e => new { e.StudentId, e.CourseId }).IsUnique();

    entity.Property(e => e.Grade).HasMaxLength(2);

    entity.HasOne(e => e.Student)
          .WithMany(s => s.Enrollments)
          .HasForeignKey(e => e.StudentId)
          .OnDelete(DeleteBehavior.Cascade);

    entity.HasOne(e => e.Course)
          .WithMany(c => c.Enrollments)
          .HasForeignKey(e => e.CourseId)
          .OnDelete(DeleteBehavior.Cascade);
});

Alternative: composite primary key instead of Id

AppDbContext.OnModelCreating
modelBuilder.Entity<Enrollment>(entity =>
{
    entity.HasKey(e => new { e.StudentId, e.CourseId });   // the pair is the key; no Id column, no extra index
});
Collections go on Student and Course, never on the junction. The junction holds two single navigations, each next to its FK.

Why Restrict: with two cascading FKs from Tickets to Users, deleting a User reaches Tickets by two paths. SQL Server refuses to create that: "may cause cycles or multiple cascade paths". Set at least one, usually both, to Restrict.

13. Moving an existing model from annotations to Fluent API

  1. Do one entity at a time. Add its modelBuilder.Entity<T> block with every rule its attributes expressed.
  2. Remove the attributes from that entity, and its using Microsoft.EntityFrameworkCore;.
  3. Run Add-Migration CheckFluentBook. If the Fluent rules match, the migration's Up and Down are empty. That's your proof nothing changed.
  4. Not empty? Read what it changes (a length, a delete behaviour, an index name), fix the Fluent rules, Remove-Migration, and try again.
  5. Empty? Remove-Migration and move on to the next entity.
  6. When done, remove the EF Core package from the Domain project. The build tells you if anything still needs it.

Managing SQL objects in one place

A beginner-friendly way to keep views, stored procedures, functions, indexes and raw SQL organised, versioned and easy to find. EF Core 8, SQL Server. The examples reuse the Author and Book model from the first tab.

The problem this solves

Without a plan, SQL ends up scattered and nobody knows which version is live.

Without a central placeWith a central place
Procedure SQL pasted as long strings inside migration filesEach object in its own .sql file, readable and highlighted in Visual Studio
Names like "usp_GetTopAuthors" typed in many classes; one typo breaks at runtimeNames defined once in a constants class; a typo is a build error
Raw queries hidden in different servicesAll queries in one class or folder
Indexes spread across entity blocksAll indexes in one file (optional)
"Which version of this view is in production?"Versioned files, each applied by one migration
Key idea: EF Core creates tables, columns, keys and indexes from your model. It does not create views, procedures or functions. Those you write as SQL and apply through migrations. This tab organises that second part, plus the names and mappings that point at it.

Step 2. One .sql file per object

Write each object with CREATE OR ALTER

Functions/fn_BookCountForAuthor.v1.sql
SQL
CREATE OR ALTER FUNCTION dbo.fn_BookCountForAuthor (@AuthorId INT)
RETURNS INT
AS
BEGIN
    RETURN (SELECT COUNT(*) FROM Books WHERE AuthorId = @AuthorId);
END
Views/vw_AuthorBookCounts.v1.sql
SQL
CREATE OR ALTER VIEW dbo.vw_AuthorBookCounts AS
SELECT a.Id        AS AuthorId,
       a.Name      AS AuthorName,
       COUNT(b.Id) AS BookCount
FROM Authors a
LEFT JOIN Books b ON b.AuthorId = a.Id
GROUP BY a.Id, a.Name;
Procedures/usp_GetTopAuthors.v1.sql
SQL
CREATE OR ALTER PROCEDURE dbo.usp_GetTopAuthors
    @Top INT
AS
BEGIN
    SET NOCOUNT ON;
    SELECT TOP (@Top)
           a.Id AS AuthorId, a.Name AS AuthorName, COUNT(b.Id) AS BookCount
    FROM Authors a
    LEFT JOIN Books b ON b.AuthorId = a.Id
    GROUP BY a.Id, a.Name
    ORDER BY COUNT(b.Id) DESC;
END
RuleWhy
One object per fileCREATE VIEW/PROCEDURE/FUNCTION must be the only statement in its batch
Always CREATE OR ALTERWorks whether the object exists or not
File name = object name + versionYou can find it instantly and see its history
Always include the schema (dbo.)Avoids objects landing in the wrong schema

MyApp.Infrastructure.csproj

Step 3. One helper to read a script

Persistence/Database/SqlScript.cs
using System.Reflection;

public static class SqlScript
{
    private static readonly Assembly Assembly = typeof(SqlScript).Assembly;

    // Example: SqlScript.Read("Views/vw_AuthorBookCounts.v1.sql")
    public static string Read(string relativePath)
    {
        // Embedded resource names use dots instead of folder slashes
        var suffix = ".Scripts." + relativePath.Replace('/', '.').Replace('\\', '.');

        var resourceName = Assembly.GetManifestResourceNames()
            .SingleOrDefault(n => n.EndsWith(suffix, StringComparison.OrdinalIgnoreCase))
            ?? throw new InvalidOperationException($"SQL script not found: {relativePath}");

        using var stream = Assembly.GetManifestResourceStream(resourceName)!;
        using var reader = new StreamReader(stream);
        return reader.ReadToEnd();
    }
}
If you get "SQL script not found", the file usually isn't embedded. Check the csproj entry, or set the file's Build Action to Embedded resource in its Properties window.

Step 4. The versioning rule (most important)

Never edit a script that a migration already uses. Add a new version instead.

Why: migrations must replay the past exactly

A new database (a teammate, a test server) runs every migration from the first one. If an old migration reads a file you've since changed, it applies today's SQL at a point in history where today's tables may not exist yet.

MigrationWhat it doesScript it reads
AddAuthorBookCountsViewCreates the viewvw_AuthorBookCounts.v1.sql
AddBookPriceAdds column Books.Price(none)
AddTotalValueToViewView now also sums pricesvw_AuthorBookCounts.v2.sql (v1 is kept as it was)
If you had edited v1 to use Price instead, a new database would run the first migration before Price exists, and fail.
Views/vw_AuthorBookCounts.v2.sql
CREATE OR ALTER VIEW dbo.vw_AuthorBookCounts AS
SELECT a.Id           AS AuthorId,
       a.Name         AS AuthorName,
       COUNT(b.Id)    AS BookCount,
       SUM(b.Price)   AS TotalValue
FROM Authors a
LEFT JOIN Books b ON b.AuthorId = a.Id
GROUP BY a.Id, a.Name;
The newest version number is always the live one. Older versions stay in the folder as history and for Down.

Step 5. Apply scripts from migrations

The migration file stays tiny: it only says which script to run.

First version

Migrations/..._AddAuthorBookCountsView.cs
public partial class AddAuthorBookCountsView : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.Sql(SqlScript.Read("Functions/fn_BookCountForAuthor.v1.sql"));
        migrationBuilder.Sql(SqlScript.Read("Views/vw_AuthorBookCounts.v1.sql"));
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.Sql("DROP VIEW IF EXISTS dbo.vw_AuthorBookCounts;");
        migrationBuilder.Sql("DROP FUNCTION IF EXISTS dbo.fn_BookCountForAuthor;");
    }
}

Changing it later

Migrations/..._AddTotalValueToView.cs
public partial class AddTotalValueToView : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
        => migrationBuilder.Sql(SqlScript.Read("Views/vw_AuthorBookCounts.v2.sql"));

    protected override void Down(MigrationBuilder migrationBuilder)
        => migrationBuilder.Sql(SqlScript.Read("Views/vw_AuthorBookCounts.v1.sql"));   // back to the previous version
}
RuleWhy
Create objects in dependency orderFunctions first, then views that use them, then procedures that use views
Drop in reverse order in DownYou can't drop a function a view still depends on
Down restores the previous version, or drops if it's the firstSo rolling back leaves the database exactly as before
Use literal names in Down SQLA migration describes one moment in time; it shouldn't change if a constant is renamed later

Step 6. Workflow: adding a new stored procedure

  1. Add the name to DbObjects.Procedures.
  2. Create the file Scripts/Procedures/usp_Name.v1.sql with CREATE OR ALTER PROCEDURE. Test it in SSMS first.
  3. Check it's embedded (the **\*.sql rule covers new files automatically).
  4. Create an empty migration: Add-Migration AddUspName.
  5. Fill Up and Down with SqlScript.Read(...) and the matching DROP.
  6. Apply: Update-Database.
  7. Call it from one repository method (step 8).

Changing an existing one

  1. Copy the latest file to the next version (v1 → v2) and edit the copy.
  2. Create a migration whose Up reads v2 and Down reads v1.
  3. Never touch v1 again.

Step 8. Call procedures from one place

Put every procedure call in one repository, so the rest of the app never sees SQL.

Persistence/Repositories/ReportRepository.cs
using Microsoft.Data.SqlClient;
using Microsoft.EntityFrameworkCore;

public class ReportRepository : IReportRepository
{
    private readonly AppDbContext _context;

    public ReportRepository(AppDbContext context) => _context = context;

    public Task<List<TopAuthor>> GetTopAuthorsAsync(int top)
    {
        var sql = "EXEC " + DbObjects.Schema + "." + DbObjects.Procedures.GetTopAuthors + " @Top = @top";

        return _context.Database
            .SqlQueryRaw<TopAuthor>(sql, new SqlParameter("@top", top))
            .ToListAsync();
    }
}
Don't write FromSql($"EXEC {DbObjects.Procedures.GetTopAuthors} ..."). In FromSql/SqlQuery, every {...} becomes a parameter value, and an object name can't be a parameter, so SQL Server rejects it. Build the name into the text, and pass only values as SqlParameter.
PieceGoes inSafe because
Procedure nameThe SQL textIt comes from your own constant, never from user input
Values (top, ids, dates)SqlParameterSQL Server treats them as data, never as SQL

Step 9. Keep raw queries in one class

Persistence/Database/SqlQueries.cs
public static class SqlQueries
{
    // {0}, {1}… are placeholders; EF turns each into a SQL parameter
    public const string BooksCheaperThan =
        "SELECT * FROM Books WHERE Price < {0}";

    public const string RaisePricesForAuthor =
        "UPDATE Books SET Price = Price * {0} WHERE AuthorId = {1}";
}
Usage in a repository
// Returns entities, and you can add LINQ after it
var cheap = await _context.Books
    .FromSqlRaw(SqlQueries.BooksCheaperThan, maxPrice)
    .OrderBy(b => b.Title)
    .ToListAsync();

// Command
int rows = await _context.Database
    .ExecuteSqlRawAsync(SqlQueries.RaisePricesForAuthor, 1.10m, authorId);
With FromSqlRaw and ExecuteSqlRaw, the values you pass after the SQL fill {0}, {1}… as parameters, not as pasted text, so this is safe. Never build the SQL with + userInput.
Long query? Put it in Scripts/Queries/Name.sql and load it with SqlScript.Read into a static readonly string, so the file is read only once.

Step 10. Map SQL functions in one class

The C# stubs and their mappings live together, so a function is defined in one file.

Persistence/Database/SqlFunctions.cs
using Microsoft.EntityFrameworkCore;

public static class SqlFunctions
{
    // Stub: never runs in C#. EF replaces the call with SQL.
    public static int BookCountForAuthor(int authorId)
        => throw new NotSupportedException("Only usable inside LINQ queries.");

    public static void Configure(ModelBuilder modelBuilder)
    {
        modelBuilder
            .HasDbFunction(typeof(SqlFunctions).GetMethod(nameof(BookCountForAuthor), new[] { typeof(int) })!)
            .HasName(DbObjects.Functions.BookCountForAuthor)
            .HasSchema(DbObjects.Schema);
    }
}
Usage
var authors = await context.Authors
    .Select(a => new { a.Name, Books = SqlFunctions.BookCountForAuthor(a.Id) })
    .ToListAsync();
// SQL: SELECT a.Name, dbo.fn_BookCountForAuthor(a.Id) FROM Authors a
This works for scalar functions (one value back). Table-valued functions need an instance method on the DbContext using FromExpression, so that one stub has to live in AppDbContext; its HasDbFunction mapping can still go in this class.

Step 11. All indexes in one file

Indexes are the exception: EF creates and updates them itself, so they stay in Fluent API, not in SQL scripts. You just collect them in one place.

Persistence/Database/DbIndexes.cs
using Microsoft.EntityFrameworkCore;

public static class DbIndexes
{
    public static void Configure(ModelBuilder modelBuilder)
    {
        // ---- Books ----
        modelBuilder.Entity<Book>()
            .HasIndex(b => b.Isbn)
            .IsUnique()
            .HasFilter("[Isbn] IS NOT NULL")                // ignore books without an ISBN
            .HasDatabaseName("UX_Books_Isbn");

        modelBuilder.Entity<Book>()
            .HasIndex(b => new { b.AuthorId, b.PublishedOn })
            .IncludeProperties(b => new { b.Title, b.Price })   // covering index
            .HasDatabaseName("IX_Books_AuthorId_PublishedOn");

        // ---- Authors ----
        modelBuilder.Entity<Author>()
            .HasIndex(a => a.Name)
            .HasDatabaseName("IX_Authors_Name");
    }
}
OptionWhat it does
IsUnique()No duplicate values
HasFilter("...")Index only rows that match (filtered index)
IncludeProperties(...)Extra columns stored in the index so queries don't touch the table
HasDatabaseName("...")Your own index name instead of EF's generated one
IsDescending()Sort order of the index columns (EF Core 7+)
Only put an index in a .sql script if Fluent API can't express it, for example a full-text index. Everything else stays here, so EF keeps it in sync through normal migrations.

Alternative: run the latest scripts at startup

Some teams skip versions and re-run every script on each start. It's simpler, with real trade-offs.

Versioned scripts in migrations (recommended)Latest scripts at startup
Files.v1, .v2… keptOne file per object, edited in place
History and rollbackYes, Down restores the previous versionNo, only what's in source control
Safe on a brand-new databaseYes, history replays in orderYes, but only after all migrations ran
ProductionApplied with the rest of the schemaApp needs permission to alter the database on every start
Best forAnything that will reach productionQuick local prototypes

Rules & checklist

  1. EF owns tables, columns, keys and indexes. Never create those in a .sql script.
  2. Scripts own views, procedures and functions. One object per file, always CREATE OR ALTER.
  3. Never edit a script a migration already uses. Add the next version.
  4. Every migration that runs a script has a Down: the previous version, or a DROP.
  5. Names live in DbObjects. No object name typed as a string anywhere else, except in migration Down SQL.
  6. Values are always parameters. Placeholders with FromSqlRaw/ExecuteSqlRaw, or SqlParameter. Never concatenate user input.
  7. All SQL calls go through repositories in Infrastructure. Services in Application call an interface and never see SQL.
  8. Test each script in SSMS first, then wire it in.
